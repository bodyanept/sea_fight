# ВВЕДЕНИЕ

## Актуальность темы

Современные браузеры обеспечивают полноценную мультимедийную и сетевую среду, достаточную для реализации интерактивных игр без установки дополнительного программного обеспечения. Технология WebSocket позволяет организовать двунаправленный канал связи между клиентом и сервером с минимальными задержками, что делает браузерную платформу привлекательной для многопользовательских игр реального времени.

Игра «Морской бой» является классической пошаговой логической игрой с формально строгими правилами и небольшим пространством состояний, что делает её удобным объектом для демонстрации полного цикла разработки сетевого приложения: от проектирования протокола взаимодействия до реализации синхронизации состояния двух клиентов в реальном времени.

В условиях локальных сетей (домашняя Wi-Fi сеть, локальная сеть учебного заведения) браузерная игра, не требующая доступа в интернет и установки клиентских программ, представляет практический интерес как инструмент развлечения и как учебный пример построения клиент-серверных систем реального времени.

# ГЛАВА 1. АНАЛИТИЧЕСКАЯ ЧАСТЬ

## 1.1. Постановка задачи

Требуется разработать веб-приложение, реализующее классическую игру «Морской бой» для двух участников, взаимодействующих через браузер в пределах одной локальной сети.

В соответствии с классическими правилами игры:

- каждый игрок располагает флот из 10 кораблей на квадратном поле 10×10: один четырёхпалубный, два трёхпалубных, три двухпалубных и четыре однопалубных;
- корабли не могут соприкасаться друг с другом ни сторонами, ни углами;
- игроки поочерёдно «стреляют» по клеткам поля соперника;
- при попадании в корабль игрок получает право на дополнительный выстрел;
- при промахе ход переходит сопернику;
- корабль считается потопленным, когда поражены все его палубы;
- победителем признаётся игрок, первым потопивший все корабли соперника.

Приложение должно реализовывать следующие функции:

- создание игровой комнаты с уникальным кодом и присоединение второго игрока по коду;
- автоматическая (случайная) расстановка кораблей с соблюдением правил размещения;
- пошаговая стрельба с мгновенной синхронизацией состояния у обоих участников;
- отображение собственного поля с кораблями и поля соперника со скрытыми кораблями;
- определение и отображение результатов выстрела (мимо / попал / потопил), а также подсказка «рядом» при промахе вблизи корабля;
- определение победителя и завершение партии;
- режим игры против компьютерного противника (бота);
- корректная обработка отключения игрока.

## 1.2. Обзор предметной области

Многопользовательская браузерная игра представляет собой распределённую систему «клиент — сервер», в которой сервер является единственным авторитетным источником игрового состояния (authoritative server), а клиенты отвечают за отображение состояния и передачу действий пользователя.

Ключевая особенность таких систем — необходимость двустороннего обмена сообщениями с малой задержкой. Классическая модель HTTP «запрос — ответ» плохо подходит для этой задачи: сервер не может инициировать передачу данных клиенту. Существует несколько подходов к решению этой проблемы:

- **Short polling** — клиент периодически опрашивает сервер. Прост в реализации, но создаёт избыточный трафик и задержки;
- **Long polling** — клиент держит запрос открытым до появления данных на сервере. Снижает задержку, но усложняет сервер и расходует соединения;
- **Server-Sent Events (SSE)** — однонаправленный поток от сервера клиенту по HTTP. Не позволяет клиенту передавать данные в рамках того же канала;
- **WebSocket** — полнодуплексный постоянный канал поверх одного TCP-соединения, установленный через HTTP-апгрейд. Является стандартным решением для браузерных игр реального времени.

Для игры «Морской бой» интенсивность обмена невысока (одно сообщение на ход), однако требуется инициированная сервером рассылка: после выстрела результат должен быть доставлен обоим игрокам, а также сервер должен уведомить игрока о начале партии и об отключении соперника. Это делает WebSocket оптимальным выбором транспорта.

Дополнительная особенность предметной области — **скрытая информация**: клиент не должен получать данные о расположении кораблей соперника. Следовательно, игровое состояние должно храниться и обрабатываться на сервере, а клиенту передаваться только разрешённая для него часть данных. Любая реализация, в которой логика проверки попаданий выполняется на клиенте, в принципе уязвима для «читерства» — извлечения расстановки кораблей из памяти клиентского приложения. Поэтому выбрана модель авторитетного сервера.

## 1.4. Обоснование выбора технологий

**Язык Python 3.10+.** Выбран как основной язык курса; обладает развитой экосистемой для веб-разработки, лаконичным синтаксисом и низким порогом входа.

**Flask 3.0** — микрофреймворк для HTTP-части приложения (отдача HTML-страницы и статики). Для данного проекта Flask выполняет единственный маршрут `/`, возвращающий игровую страницу, — тяжёлые фреймворки уровня Django избыточны.

**Flask-SocketIO 5.3** — библиотека, реализующая протокол Socket.IO поверх WebSocket. Socket.IO предоставляет удобную событийную модель (`emit`/`on`), автоматический fallback на long polling при недоступности WebSocket, а также встроенный механизм **комнат** (`join_room`, `emit(..., room=code)`), который естественным образом отображается на игровые комнаты приложения. В проекте используется асинхронный режим `threading`, обеспечивающий совместимость с актуальными версиями Python без дополнительных зависимостей.

**Клиентская часть** — HTML5, CSS3 и ванильный JavaScript без сборщиков и фреймворков. Это упрощает развёртывание (не требуется шаг сборки) и делает код максимально прозрачным для учебных целей. Клиентская библиотека Socket.IO подключается с CDN с каскадным резервированием на локальную копию `/static/socket.io.min.js`, что сохраняет работоспособность при отсутствии интернета в LAN-сценарии.

**Хранение состояния** — в памяти процесса (словари `rooms` и `sid_to_room`). Для игры с двумя участниками в LAN это достаточно и исключает необходимость в СУБД; следствием является очистка комнат при перезапуске сервера, что для данной задачи допустимо.

## 1.5. Требования к разрабатываемому приложению

**Функциональные требования:**

- FR-1. Создание комнаты с автоматической генерацией пятизначного числового кода.
- FR-2. Присоединение к существующей комнате по коду; отказ при несуществующем коде или заполненной комнате.
- FR-3. Автоматический старт партии при подключении второго игрока со случайным выбором первого хода.
- FR-4. Автоматическая расстановка кораблей для обоих игроков по классическим правилам.
- FR-5. Обработка выстрела: проверка очерёдности хода, валидности координат, вычисление результата («мимо»/«рядом»/«попал»/«потопил»), передача хода или сохранение его за стрелявшим.
- FR-6. Рассылка результата выстрела обоим участникам комнаты.
- FR-7. Определение окончания партии и уведомление о победителе.
- FR-8. Режим игры с ботом, делающим ходы автоматически.
- FR-9. Уведомление осташегося игрока при отключении соперника и очистка пустых комнат.

**Нефункциональные требования:**

- NFR-1. Работа в LAN без доступа в интернет (кроме разовой установки зависимостей).
- NFR-2. Кроссплатформенность клиента: любой современный браузер на ПК или смартфоне.
- NFR-3. Скрытие расположения кораблей соперника от клиента.
- NFR-4. Устойчивость к повторным выстрелам по одной клетке и к невалидным данным от клиента.
- NFR-5. Задержка доставки хода — не более 1 с в локальной сети.
